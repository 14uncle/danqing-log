## 一句话

手势层已在选区/复制那批补齐, 但**每个手势有没有反馈**从没被统一量过 —— 现有反馈
几乎全是撞出来的 (近四轮实机回归, 没有一条是「手势做不到」, 全是「做了看不出来」)。
这次把手势与反馈**当成一件事**, 按**可判定的三问**把全应用**已实现**手势扫一遍,
粗糙点清零并落守卫。**进 v1.0, 阻塞发布**。

## 结论 (用户逐行确认)

- **Outcome**: 现装这个二进制上, 每个已实现手势都过「三问」(见下), 粗糙点清零;
  每条修复配一条回归锁, 使「反馈缺失」不再靠实机撞出来才发现。
- **User**: v1.0 首发用户 (读大文件日志的后端/运维) —— 打磨的是他们上手头五分钟
  会撞到的那层。但要如实记: **本仓至今没有第二位用户**, 实机走查由产品所有者代跑,
  这层代理的局限与 clipboard 那次「自代理付费测试已废」是同一个问题的弱化版。
- **Why now**: 发布基线已合并且工作区干净 (`b2d8351`), 而**反馈类打磨几乎必然动到
  截图取景范围** (hover 态 / 选中高亮 / 侧栏提示行 / 状态栏文案) —— 先拍必废。
  发布链本就挂在「待逐项点头」上, 无已承诺发布日期可失约。
- **Success**:
  - 「手势 × 反馈」矩阵走完 + 用户实机逐条确认**无新缺口** —— 完成标志是
    **矩阵走完**, 不是「修完报出来的那几条」;
  - 每个粗糙点带一条守卫或回归锁 (沿用本仓习惯);
  - `cargo fmt` + `cargo clippy --all-targets -- -D warnings` + 测试全绿。
- **Constraint**:
  - **阻塞发布** —— 截图 / 打 tag / GitHub Release / 商店提交**全部等这批落地**;
  - 密度不许降 (沿袭 ui-redesign 的用户原话「不允许」);
  - 框架挡路就动框架 (ui-redesign 那轮的授权**延续**), 联动走既有链路
    (`cp tools/local-patch.toml` → 改兄弟仓 → 先 push → 本仓 `cargo update -p` 复钉 → 两仓分别提交);
  - 「该有而没有的手势」**不自动进本次批量** —— 那等于加功能, 单独立项。
    **例外判据 (2026-09-14 裁定 5)**: 界面**已经承诺**该手势的 (滚动条画了拇指) 补进本批;
    界面上毫无承诺的 (拖放 / 排序 / 快捷键) 维持单独立项。
- **Out of scope**:
  - **(b) 顺手 / 竞品对拍** (klogg / LogViewPlus 上有的手势我们没有、或它们反馈更清楚)
    → **v1.x**。理由: 本仓已被「判据跟现象对不上」坑过两回 (拿 WCAG 对比度量大面积
    色差 / 拿页面底当屏幕上的邻居), 主观判据在这条产品线上有前科; 且上一轮对竞品调研
    时 **WebFetch 被网络策略整体拦截**, 结论只能按「待验证」看待 —— 拿它当发布前阻塞
    判据风险太高。真要做, 先解决调研通路。
  - 视觉色板 / 字号 / 面阶梯 —— ui-redesign 五模块已闭环, 不回头重开;
    **例外**: 若矩阵证明某处「视觉本身就是反馈」(如选中色与行底色同 token = 看不出
    选了哪一格), 那是反馈缺陷, 拉进来。
  - v1.x 付费层 / add-on 内购。
  - 行多选 (Shift/Ctrl) —— 已裁挂 v1.x。
  - D3/D4 待裁项 (浅色两条着色路径分叉 / 框架 `composite_over` 混在 sRGB 空间)
    —— 是**视觉判据**问题, 不在本次; 除非矩阵把它照成分叉的反馈。

> 两条锁定假设 (agent 提议, 用户 yes 时一并确认): **框架改动授权延续** /
> **手势缺失单独立项**。

## 判据: 每个手势三问

| # | 问 | 粗糙点的形态 |
|---|----|-------------|
| 1 | 按下有没有**即时**变化? (<100ms 内的视觉或光标) | 手指动了, 屏幕没动 |
| 2 | 结果有没有被**留住**? (高亮 / 状态栏 / 侧栏 / 图标态) | 做了, 但看不出做的是哪一个 |
| 3 | 不可用时有没有**说清为什么**? | 点了没反应, 也不说为什么 |

三问全过 = 该手势合格。**只量已实现的手势** —— 三问的前提是「有个手势」,
「该有而没有的手势」走另一条路 (见下节)。

**反面教材三条 (都来自已发生的实机回归, 用来校准尺子)**:

- 侧栏 `.log` 只读态被产品所有者本人读成「坏了」→ 违第 3 问 (两种模式侧栏同貌,
  谁也没说「这里不可点」);
- 表格单元格高亮与整行选中同 token → 违第 2 问 (整行同色, 看不出选的是哪一列,
  而 Ctrl+C 只复制那一格 = **视觉与结果自相矛盾**);
- 可点行无 hover (2026-09-13 验收反馈) → 违第 1 问。

## 扫法: 「手势 × 反馈」矩阵, 双侧走查

- **枚举来源 (代码侧)**: 本仓事件入口 (`src/main.rs` / `src/view.rs` /
  `src/histogram.rs` / `src/settings.rs` / `src/tray.rs`) × 框架
  `danqing/src/window/handler.rs` **实际匹配的 `WindowEvent` 全集** ——
  已查实为 `{CursorMoved, CursorLeft, MouseInput, MouseWheel, KeyboardInput, Ime,
  ModifiersChanged, Focused, CloseRequested, Resized, Moved, RedrawRequested}`。
  这是「手势」的**权威上界**, 不靠自己回忆补齐。
- **实机侧**: 用户按矩阵逐条对, 逐格标合格 / 粗糙 / 缺失。
- **为什么必须双侧** (本仓两个已发生的漏检各占一半):
  - **代码侧会漏** —— 「列表区末行下方空白双击, 画面上无任何高亮, Ctrl+C 却复制
    第 0 行该列的值」是 review 才抓到的, 实机几乎撞不到;
  - **实机侧会漏** —— 「`.log` 侧栏只读态被读成坏了」代码上看完全正常, 是产品
    所有者上手才发现的。
  任何单侧枚举都会漏掉另一半。
- **矩阵落点**: 预计 `tasks/todo-interaction-polish.md` (spec / plan 阶段定)。

## 「手势缺失」不是本次范围

三问量的是反馈, 前提是手势存在。已查实一条, 记在此免得下次又当它是反馈问题:

- `src/open.rs` 模块头与 `OpenKind::Fresh` 注释都写「Ctrl+O·**拖拽**」,
  但**拖拽打开从未实现**。证据两条: ① 本仓 `src/` 无 `DroppedFile` / `HoveredFile`
  命中; ② 框架 `danqing/src/window/handler.rs` 匹配的 `WindowEvent` 全集里**没有**
  `DroppedFile` / `HoveredFile` (winit 0.30 的拖放事件名) —— 即窗口根本没接这条事件,
  产品侧无从收到。
- **处置**: 该「拖拽」是拆分/起草期的**路径标签遗留**。本次只修**注释口径**
  (把不存在的路径从注释里去掉); 真要做「拖文件到窗口打开」= 新功能, 单独立项。

## 裁决记录 (interview 逐轮)

| 轮 | 问 | 用户裁定 | 推论 |
|----|----|---------|------|
| 0 | 本次访谈的对象是什么 | **交互打磨** (既不是发布链收尾, 也不是 v1.x 付费层, 也不是待裁项) | 这是一件此前没立过项的事, 需从零澄清边界 |
| 1 | 「交互」指哪一层: (a) 手势 / (b) 反馈 / (c) 一体 | **(c) 两者视为一体**, 重心在反馈 | 手势已由选区/复制那批补齐; 没被统一量过的是反馈 |
| 2 | 「一遍」怎么算走完: 谁枚举 | **代码侧矩阵 + 实机侧逐条对, 双侧都走** | 单侧必然漏一半 (两侧各有前例); 完成标志 = 矩阵走完 |
| 3 | 「打磨好」的停止条件: 粗糙点清零 / 顺手 / 两者 | **(a) 粗糙点清零**; (b) 顺手与竞品对拍**划给 v1.x** | (a) 可枚举可修完; (b) 需竞品对拍素材, 而调研通路当前被网络策略挡着, 不能当发布前阻塞判据 |
| 4 | 与发布链先后: 阻塞 / 并行 / 发布优先 | **(a) 阻塞发布** | 反馈类打磨几乎必然动到截图取景范围 (hover / 高亮 / 提示行 / 状态栏文案), 先拍必废 |
| — | 两条默认 (框架授权延续 / 手势缺失单独立项) | **yes 时一并确认** | 框架挡路可动; 拖放这类「缺失」不进批量 |
| 5 | **滚动条**: 画了 track/thumb 却不能拖 = 反馈缺陷还是手势缺失 | **本批补拖拽** | **越过了「手势缺失单独立项」那句的字面** —— 裁定理由: 行锚定数学已有 (`row_at`), 是**补全界面已经承诺的手势**, 不是新增功能语义; 且「画了不能拖」是违第 1 问的直接形态 |
| 6 | **表头**: 列名看着可点, 实际无 hover 无点击 | **不补 hover, 排序/拖宽单独立项** | 给一个**不存在的手势**加 hover 等于教错 (本仓已有先例: 侧栏不可点行有意不给 hover); 排序是新功能 (新状态 + 新 UI), 与「不加功能」冲突 |
| 7 | **框架无光标形状 API** (`CursorIcon` 全库零命中, 违第 1 问) | **本批补一个薄 API** | 光标形状是「按下即时变化」最标准的原语之一; winit 0.30 有 `set_cursor`, 薄封装 + 进出区域复位。**第四条约束「框架挡路就动框架」的第二次动用** |

**裁定 5/6/7 的连带后果 (写给下一次的自己, 免得被 intent 字面砍掉)**:

- 「手势缺失单独立项」这条**有例外** —— 判据是**界面是否已经承诺了该手势**:
  滚动条**画了拇指** = 已承诺 → 补进本批; 拖放/排序/快捷键**界面上没有任何承诺**
  → 维持单独立项。
- 光标 API 使 P2/P3/P4 等一批 hover 缺口的表达多一条通道 (光标 + 视觉双通道),
  故框架模块 M1 是产品侧 M2/M3 的前置。
