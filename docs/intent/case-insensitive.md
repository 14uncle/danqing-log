# Intent: 搜索/过滤默认大小写不敏感 (case-insensitive)

> @author 十四叔 · @date 2026/09/15
> 来源: 用户直接发起 —— 先质询性能影响, agent 实测对拍后用户当场两项裁定
> 下游: `docs/specs/SPEC-case-insensitive.md`

---

## 一句话

搜索与过滤全面改为**默认大小写不敏感** —— 敲 `error` 搜不到满屏 `ERROR` 是日志
查看器头号的「第一分钟坏印象」。实测证明性能代价在无感量级; 真正要管的不是性能,
是**口径一致性** (直方图逐桶相等红线 / 高亮同源 / GBK 字节面)。

---

## 裁定记录 (2026-09-15, 用户)

1. **默认不敏感, 不加开关** (用户原话「默认不敏感」)。要敏感的正则用户在模式内写
   `(?-i)` —— 零代码逃逸舱 (UTF-8 搜索路径的查询本来就是裸正则)。
2. **GBK 尾字节假命中类: 接受写明, 不加守卫** (用户「按你建议」→ agent 建议接受)。
   理由: 该误中类在大小写敏感版**今天已存在** (字节面匹配本就不知字符边界), 不敏感
   只把每个位置的候选字节值 ×2, 不引入新的错误类别; 实测 32 万行中文 GBK 样本
   **零假命中**; 触发需「GBK 尾字节恰为查询词首字母 + 紧跟查询词剩余字母的 ASCII
   文本」同时成立; 后果是行级假命中 (多显示一行), 不崩不丢数据。后路已想清 ——
   命中行级 GBK 边界扫描 (只对命中行做, 稀疏命中近零成本), 实机真撞到再修。
3. **时机: 进 v1.0, 阻塞发布**。截图 / 打 tag / GitHub Release / 商店提交全部
   等本模块落地验收; 本模块不动截图取景范围内的视觉, 不废已备素材。
4. **GBK 过滤栏非 ASCII 查询词缺口: 单独立项**。候选修法已留档 (spec §8 Q2)。

> **plan 阶段修正 (2026-09-15)**: 直方图**行口径**分类器保持敏感 —— 「敏感防正文
> 污染」是 `levels.rs:110` 的既定设计, 且 .log 桶只读不受逐桶相等约束; 只有
> **字段口径** (可点) 被 D2 红线强制跟随不敏感。详见 spec D7 修正记录。

## 实测弹药 (性能不是障碍的证据)

2026-09-15 本机 release 构建, 1GB 演示文件 (genlog 重新生成, 行数与历史记录逐字节
一致: 明文 6,349,886 行 / JSONL 4,021,125 行), 热缓存, logbench 直出。

**搜索路径** (`LogFile::search` 单线程 regex `find_iter`, 敏感 → `(?i-u)` 不敏感):

| 模式形态 | 敏感 | 不敏感 | 倍数 |
|---|---|---|---|
| `ERROR` (短字面, 最常用) | 74ms | 121ms | 1.6x |
| `ERROR\|FATAL` (交替) | 114ms | 119ms | ~1.0x |
| `user_42\d{4}` (字面+正则后缀) | 96ms | 649ms | **6.8x** (已知最差形态) |
| 时间戳 `\d{4}-\d{2}-…` (无字母) | 1177ms | 1172ms | 1.0x |
| `e` (病态单字母) | 2413ms | 2352ms | 1.0x |

**过滤路径** (1GB JSONL, 并行):

| 子句 | 敏感基线 | 不敏感代价 |
|---|---|---|
| Flat `level=ERROR` | 40ms | **≈0** —— 键的 memmem 粗筛不动, 只换已提取短 token 的最终比较 |
| Bare 裸词 (.log 整行子串) | 82ms | memmem 无不敏感模式 → per-line `(?i-u)` 正则, 参照搜索短字面 ~1.5x |

**禁路实测**: 字段**键**若也走正则不敏感 (`(?i-u)"level":"ERROR"`), 1822ms/1GB
(22x 退化 —— prefilter 被每个键名开头的 `"`+字母打爆)。正解 = 拿用户键名去列发现
结果里不敏感查表、改写成真实键名, memmem 照旧, 零成本。

**GBK 构造实测** (demo-cn-gbk.log, 32 万行): `(?i)(?-u)error` 与手工展开
`[eE][rR][rR][oO][rR]` 命中**逐字节一致** (7884 命中行 / 8347 总命中, 恰为该文件
ERROR 级别行数 → 零假命中) —— `(?i)` 前缀对 `(?-u)` 字节转义**折叠成立**, GBK 侧
构造 = 既有字节字面化前面加 `(?i)`, 无需手工逐字节展开。

**顺带发现的既有缺口** (与本模块无关, 如实记): 过滤栏非 ASCII 查询词对非 UTF-8 文件
**无效** —— `--filter "订单"` 在 GBK 文件上 0/320596 命中 (查询词 UTF-8 字节直接
比对 GBK 文件字节)。搜索栏无此问题 (有 `encode_query` 转码)。处置见 spec §8 Q2。

## 结论

- **Outcome**: 搜索栏 / Bare 过滤 / Flat 过滤 (值+键) / 直方图分类器 / 高亮,
  **五处同口径**默认大小写不敏感; 每处配守卫; 直方图「桶计数 = 筛选结果」的
  构造保证 (SPEC-level-histogram D2) 在混合大小写 fixture 下延续。
- **User**: 读大文件日志的后端/运维 —— 日志级别、关键词的大小写形态从来不是
  用户想记的; 竞品基准: klogg 默认敏感可切, VS Code 系默认不敏感, 我们取后者。
- **Why now**: v1.0 发布链停在「截图待拍」上, 二进制尚未冻结; 本模块不动任何
  截图取景范围内的视觉, 不废截图素材。时机已裁: **进 v1.0, 阻塞发布** (裁定 3)。
- **Success**: spec §0 四条 (五处同口径 + 性能预算达标 + 三件套全绿 + 人工验收六条)。
- **Constraint**:
  - 不加开关、不加配置项、不加 UI 元素 (裁定 1);
  - 只动**本仓 + danqing-logfile**; danqing 与 danqing-encoding 零改动
    (`bytes_as_literal_regex` 在 encoding 仓, 但 `(?i)` 前缀由调用方加, 函数本身不动);
  - 性能预算线 (spec §4) 不许破 —— 打开管道零影响, 查询期全形态 1GB 亚秒。
- **Out of scope**:
  - 大小写开关 / 设置项 (裁定 1 的反面);
  - Verify 点路径的**键**不敏感 (嵌套键不在列发现表层, 小众路径, 写明敏感);
  - GBK 过滤栏非 ASCII 查询词缺口 (既有缺陷, 已裁**单独立项** —— 裁定 4);
  - 全角字母 (Ａ-Ｚ) 折叠 —— GBK 里有但无实际需求, 不造。
