## 丹青日志 LogLens

Windows 上的大文件日志 / JSONL 查看分析器，v1.0.0 今天发布。

免费，源码开放（MIT OR Apache-2.0）。便携版是一个不到 5MB 的 zip，解压即用，不写注册表。

[图: 首图 —— JSONL 表格 + 左侧级别直方图]

先给数字（1 GiB 文件、热缓存、release 构建）：

| 指标 | 明文日志 | JSONL |
|---|---|---|
| 索引 | 92 ms | 94 ms |
| 搜索（`ERROR`，默认大小写不敏感） | 115 ms | 129 ms |
| 字段过滤（`level=ERROR`） | — | 40 ms |
| 随机访问 | 0.52 µs/行 | 0.58 µs/行 |
| 打开（冷 / 热） | ~600 ms / ~90 ms | 同 |

行索引内存 ≤ 16 MB / 1 GiB。完整测试条件在仓库的 `PERFORMANCE_REPORT.md`。

## 功能速览

- **打开**：启动传参或 `Ctrl+O`，索引在后台线程跑，GB 级文件全程可响应，可以随时取消，也可以在索引中直接开另一个文件
- **搜索**：正则全文扫描，默认大小写不敏感（要精确匹配写 `(?-i)`），可见区高亮 + 命中逐跳导航
- **JSONL 表格**：自动检出 → 列发现 → 列化成表格；嵌套对象（比如 `user`、`tags`）按 `→` 展开成子行；字段过滤迷你语法 `level=ERROR status=50*`（空格 AND、尾缀 `*` 前缀通配）跑在工作线程，不冻界面

[图: 正则搜索 `status=5\d\d`，带命中高亮和底栏命中数]

- **级别统计侧栏**：FATAL / ERROR / WARN / INFO / DEBUG / 其他 六桶计数 + 对数刻度横条，JSONL 下点柱条直接筛出该级别，`Ctrl+L` 显隐

[图: 点了 ERROR 柱之后，列表只剩 ERROR 行]

- **编码**：UTF-8（含 BOM）/ UTF-16 LE·BE / GBK 自动检测。GBK 走原字节索引 + 行级解码，中文可以正常搜（字面量，无正则）

[图: GBK 中文日志那张]

- **tail 跟随**：250ms 节流轮询，新行 1 秒内出现；上滚自动脱离，外部截断 / 轮转自动重建索引
- **选区 / 复制**：双击选词按「混合连接器规则」——时间戳、IP、`level=ERROR`、路径、URL 整个选中，英文按单词断开，中文逐字；表格里双击单元格复制完整值（不受列宽截断影响），选中行复制整行原文
- **其他**：浅色 / 暗色主题、系统托盘、行锚定虚拟视口（2 亿像素域不失真）

## 架构：没有 Electron，UI 框架也是自己写的

整个应用是 Rust，UI 没有用任何现成框架的封装——是自家产品线的 `danqing`（winit + wgpu 自绘）。这是体积不到 5MB、启动到可见约 800ms 的原因。

引擎层拆成了三个独立开源 crate：`danqing`（UI）、`danqing-logfile`（mmap + 行索引 + 搜索 + JSONL）、`danqing-encoding`（编码检测/转码），后两个零 UI 依赖，可以单独拿去用。

几个关键的实现选择：

- **行索引是步进表，不是逐行偏移表**：`memchr` SIMD 扫 `\n`，每 `INDEX_STRIDE` 行记一个绝对偏移。1 GiB 文件索引内存 ≤ 16 MB，这是「大文件」和「常驻内存小」能同时成立的原因
- **搜索直接在字节上跑**（`regex::bytes`），不做 String 转换；GBK 文件不转码建索引，原字节索引 + 按行解码
- **JSONL 列化零 parse**：字段提取用 `memmem` 按字节找，不整行 serde 解析；只有列发现阶段采样解析一小段

## 性能故事一：9312ms → 34ms，慢的不是扫描

级别侧栏上线后，用户报「加了日志级别统计就变慢了」。

我第一反应是去量扫描本身，量出来都很正常——直到用户给了两条**同机对照**：字段口径计数 9312ms（1 GiB JSONL，483 万行），行口径计数 417ms（1 GiB 明文，635 万行）。22 倍。

问题在于：字段口径扫的字节其实**更少**（每行找到 `"level":` 就返回），却慢了 22 倍。所以慢的不是扫描，是**每行的两次构造**——`field_needle` 每行分配一个 `Vec`，而且 `memchr::memmem::find` 是懒构造：每次调用都为 needle 重做一遍 prefilter 分析。几百万行，每行重来一次。

修法是把 needle 和 `Finder` 各建一次、逐行复用（`jsonl::FieldExtractor`）。用户机器上 9312ms → 34ms，274 倍。

两条教训：热路径上「每行一次的小分配」都是嫌疑犯；**对照组比绝对值有用得多**——没有用户给的那组对照，我还在扫描路径上瞎量。

## 性能故事二：状态栏说 92ms，用户却等了 10 秒

另一次，用户打开 1 GiB JSONL，状态栏明明白白写着「索引 92ms」，内容却要 ~10 秒才出来。

慢的不是索引，是**列发现**：它按 512 行采样、用 serde_json 完整解析每一行——成本随**行宽**无界。用户那个文件平均 563 KiB / 行，采样一读就是 200 MiB、3.17 秒（serde 解析这种「上万小对象」的形状只有 ~60 MB/s）。

修法：采样加**字节预算**（4 MiB，行宽 ≤ 8 KiB 时不生效，普通日志零影响），值宽度探测有界化。同一个文件 3.17s → 71ms。

但这件事真正的教训是：**状态栏那个「索引 92ms」只是打开管道的其中一段**，它从来不等于用户在等的时间——列发现和级别计数都不算在里面。数字与体感不符，多半是数字量错了对象。后来进度显示改成了阶段感知：索引 → 列发现 → 计数，每段单独报。

## 已知边界（诚实清单）

- UTF-16 转码副本内存翻倍（1 GiB → 约 500 MB 副本）；> 2 GiB 文件未验证
- JSONL 列化只认扁平顶层字段；嵌套对象以子行展开看，不进列
- GBK / Latin-1 文件搜索退化为字面量，无正则语法
- 表格列无拖拽 / 显隐 / 重排（v1 欠账，会在免费层补）
- 明文日志下级别侧栏只读（纯文本没有字段过滤语法，点柱条给不出等价筛选）
- 搜索命中上限 100 万条；不做 ANSI 转义渲染

## 它是怎么做到快的

三个核心决策。

**第一，行索引是步进表，不是逐行偏移表。** 用 `memchr` 的 SIMD 扫换行符，每隔固定行数记一个绝对偏移。1 GiB 文件，索引内存 ≤ 16 MB。这是「大文件秒开」和「常驻内存小」能同时成立的原因。

**第三，JSONL 列化零 parse。** 字段提取按字节找（`memmem`），不整行 JSON 解析。402 万行的 JSONL 文件，字段过滤 `level=ERROR` 只要 40ms。

## 两个让我印象深刻的性能事故

**事故一：9312ms → 34ms。** 级别统计功能上线后，用户报「加了统计就慢」。我在自己机器上怎么量都正常，直到用户发来同机对照：字段口径计数 9312ms，行口径 417ms，22 倍——而字段口径扫的字节明明更少。最后定位到：慢的不是扫描，是每行都在重新分配 needle、重新构造搜索器的 prefilter。几百万行，每行重来一遍。把构造挪到循环外，9312ms 变成 34ms，274 倍。教训：热路径上「每行一次的小分配」都是嫌疑犯，以及，对照组比绝对值有用。

**事故二：状态栏说 92ms，用户等了 10 秒。** 查下来慢的是列发现——它按 512 行采样解析，成本随行宽无界，用户那个文件平均 563KB 一行，采样一读就是 200MB。加字节预算后降到 71ms。但真正的教训是：状态栏的「索引 92ms」从来不等于用户在等的时间，它没算列发现和计数。数字和体感对不上，多半是数字量错了对象。
