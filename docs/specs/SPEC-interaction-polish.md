   模块之前的 (那之后 main 从 56 涨到 74), 583 是更早的框架基线)。

**三问的可判定化** (反面教材全部来自已发生的实机回归, 用来校准尺子):

| 问 | 合格 | 不合格的形态 |
|----|------|-------------|
| 1 即时 | 按下后 <100ms 内画面或光标有变化 | 手指动了屏幕没动 (P1–P11) |
| 2 留得住 | 能指出**哪一个对象**被作用了 | 做了但看不出作用于谁; 或视觉与结果**自相矛盾** (P14–P18) |

**尺度沿用既有守卫**, 不新造: 常驻面 AA ≥4.5、瞬时面 (hover/选中) ΔL\* ≥3、
相邻面两两 ≥3 (前例 `table_surfaces_are_separated_from_their_neighbours`)。

## 2. M1 `danqing:cursor-focus-routing` (框架)

### Objective

补上三问所需、而框架**今天给不了**的通路。**只给机制, 不改任何既有行为**。

**实施期收缩 (2026-09-14)**: 原计划四节 (光标 / 屏障 / 滚轮回退 / token 槽位),
读码后 **M1.3 与 M1.4 双双撤回** (机制本就存在 / 分层反了, 各有专节记录) ——
**M1 收敛为 光标形状 API (M1.1) + `collect()` 认模态屏障 (M1.2) + 焦点可见 (P8)**。

**覆盖缺口 (如实记, 由本 spec 收口时发现)**: 本表原把 **P6/P30 也挂在 M1**,
现两者都**不在 M1**: P30 转入 M4 (产品侧), **P6 (过滤栏 `chromeless` 无焦点描边)
改归 M2** (产品侧画, 与 M2 的「视觉通道」同族)。M1 只留 P8/P9/P31。

### M1.1 光标形状 API (新)

**现状 (查证)**: `danqing` 全库 `CursorIcon` / `set_cursor_icon` **零命中**;
`src/window/handler.rs:47` 已持有 `window: Option<Arc<WinitWindow>>`,
winit 0.30 具备 `set_cursor` → **薄封装可行, 不引依赖**。
缺口后果: 悬停文本不变 I-beam、可点区不变 hand —— 三问第 1 问最标准的原语缺失。

**设计 (与焦点同源 —— 本模块的核心选择)**:

- `Widget` trait 新增 `fn cursor_at(&self) -> Option<CursorIcon> { None }` ——
  与 `focusable()` / `focus_id()` / `modal_barrier()` 同款「默认实现 + 框架调度」模式,
  **未实现的控件一行不改**;
- 框架新增 `cursor_at(root, pos) -> Option<CursorIcon>`, **复用 `hit_focusable` 那一趟
  `visit` walk** (`src/widget/focus.rs:199-249`) —— 同一套模态屏障 (`:222`) 与
  祖先裁剪 (`:214-219`) 语义, **单一真身**, 不另推一份命中几何
  (本仓 2026-09-14 刚为「命绘各推一遍」吃过一轮苦头, 见 S1–S3);
- Handler 求值并 apply; **无命中 → `CursorIcon::Default`**。

**不变量**:

1. **每帧重新求值** —— 因此**不需要**「离开控件」事件。矩阵 §4 的 G9
   (**经查为伪缺口**, 本 spec 更正普查结论): `src/widget/layout/flow.rs:268-287`
   把 `CursorMoved` **广播全树**, 每个组件都能自查 `contains`, 离开语义天然成立;
2. **光标不锁定**: 任一帧无命中即回 `Default`, 不依赖任何 leave 事件复位
   —— 这是它比「组件自己 set/unset」更稳的地方;
3. 未实现 `cursor_at` 的控件, 行为与今天**逐字节相同**。

**消费方 (本批)**: 文本区 I-beam; 行 / 桶行 / 按钮 / 滚动条拇指 / 可点区 PointingHand;
不可点区 Default。**P2 P3 P4 P5 这些 hover 缺口由此获得第二条通道。**

**验收**: ① 与 `hit_focusable` **对拍同一组几何** (同一 pos 下两者命中同一节点);
② 模态屏障下不从卡后取光标; ③ 无命中回 `Default`; ④ 未实现 `cursor_at` 的控件返回值恒 `None`。

### M1.2 `collect()` 认模态屏障 (P31)

**现状 (查证)**: `src/widget/focus.rs:147-168` 的 `collect()` 遍历全部 `focusable()` 节点,
**不看 `modal_barrier()`**; 而**同一文件**的 `visit()` (`:222`) 看。
后果: 设置卡开着时 Tab 能落到卡后被盖住的 LogView / Bar 上, 按 Tab 看不到任何事发生。

**依据 (不是发明)**: `hit_focusable` 的文档注释 (`src/widget/focus.rs:193-198`) 记着
它修过的**同款** bug ——「danqing-log 2026-09-14: 设置卡里的下拉点击后, 焦点落到底层
全 rect 的 LogView, 键盘导航漏成滚动」。**P31 是同一个 bug 的 Tab 通道。**

**改法**: `collect()` 施加与 `visit()` **同一规则** (开态屏障只深入最上层那个,
屏障外兄弟子树不进链)。

**不变量**: 模态开时 Tab 在卡内**成环**, 不落到卡后; 模态关时链条与今完全相同。

**验收**: ① 屏障外的可聚焦节点不进 chain; ② 屏障内多节点 Tab 成环 (首尾相接);
③ 无屏障时 chain 与今逐项相同 (回归锁); ④ 与 `visit()` 的屏障用例**共用夹具**。

### M1.3 ~~未认领滚轮回退~~ —— **2026-09-14 实现期撤回 (机制本就存在)**

原计划在框架加一个与 `propagate_unhandled_keys` 对称的「未认领事件回退」开关。
**读调用链后发现不必** —— 该机制**已经存在, 且比键盘那套更宽**:

- **框架侧** `src/window/handler.rs:983-985`:
  ```rust
  if result == crate::widget::EventResult::Ignored {
      self.app.event(&internal);
  }
  ```
  未认领的**鼠标事件本来就无条件回退给应用** (键盘才需要 `key_falls_back_to_app` 的
  opt-in)。滚轮也不例外。
- **应用侧** `danqing-log/src/main.rs:1222-1231`:
  ```rust
  let Event::Key { key, pressed: true, .. } = event else { return };
  ```
  滚轮**到达了应用, 被应用自己丢掉**。

**故 P30 的根因在产品侧, 框架零改动。** 修法: 本仓 `LogApp::event` 处理
`Event::MouseWheel`, 按位置把未认领的滚轮转给列表滚动 —— 归 **M4** (手势的归属)。
注意 `delta` 框架**不归一** (`LineDelta` / `PixelDelta` 两种, 见普查 G10),
产品侧两条都要接。

**撤回编号不复用**, 免得后续挪位。

**方法论 (两条合起来看, 比分头看有用)**: 这一条与 M1.4 都是「plan 里的框架活其实
不用干」, 而且**都来自读代码本身、而非信普查**。普查在 `flow.rs` 那一层说的是对的
(「按点子命中不回落」), 漏的是调用链**上一层**的 handler ——
**子代理的结论要在调用链的上一层再核一次**, 局部正确不等于全局正确。

### M1.4 ~~四态分通道 token 槽位~~ —— **2026-09-14 实现期撤回 (前提有误)**

原计划由 M1 在框架 `Theme` 上加「分通道 token 槽位」。**动工前读码, 发现前提是错的, 撤回。**

本仓的真实分层是「框架给**通用**调色板 (`LightTheme`/`DarkTheme`) → 产品 `LogTheme`
(`src/config.rs:144`) **逐方法转发** → **产品语义色放产品侧函数**」。
这不是我的推断, 是**本仓自己写在注释里的规矩** (`src/view.rs:126`):

> 与 `bookmark_color` / `expand_block_bg` 同一处理: **产品语义放产品侧**。

三个先例都在产品侧写死浅/深两套值 (`row_band_bg` `view.rs:128` /
`row_hover_bg` `:150` / `cell_highlight_colors` `:166`), 守卫也在产品侧
(`table_surfaces_are_separated_from_their_neighbours` `view.rs:2356` /
`row_band_and_hover_are_separate_channels`)。

把 `hit_row` / `selection_cell` 这类**日志查看器语义**的颜色塞进通用框架 `Theme`,
是产品概念泄漏进框架 —— 与既有分层相反。

**连带后果**:

- **M2 的四态分通道改为纯产品侧改动** (照 `row_hover_bg` 的先例, 加产品侧取色函数
  + 产品侧守卫), **框架零 token 新增**;
- **M3 的 notice 配色同样不需要新 token** —— `danger()` 框架已有, 中性回执用
  `text_secondary()`;
- **M1 收敛为 T1 / T2 / T3 三节**。

**方法论记一条**: 这一条是「框架先出现、产品后赋值」写在 plan 里、看着很顺,
实际与本仓分层相反 —— **分层的判据在代码注释里, 不在架构直觉里**。

**明确不动**: `token_at` / `text::selection` (上一模块刚改完) / `focusable` / `focus_id` /
`hit_focusable` 的**点击定焦**行为 / 既有键盘回退行为 / `title_bar` 的本地双击实现。

## 4. M3 `silent-refusal` (本仓)

### Objective

「按了没反应, 也不说为什么」不再沉默 —— 先造**一根统一的管子**, 再把所有沉默项接上去。
**不新增弹窗、不新增模态** (密度不许降)。

### 地基: 反馈通道与错误态独立视觉 (P27)

**现状 (查证, 我读源码复核过)**: 打开耗时 / 过滤统计 / **打开失败 / 轮转 / 选区超限 /
正则无效** 全部拼进**同一个** `self.status` 字符串, 用 `th.text_secondary()` 绘制
(`src/view.rs:1408-1414`) —— **错误与常态信息同色同字号, 视觉上不存在**。

**改法**: 状态栏分两条通道 —— **常态信息** (打开耗时 / 行数 / 跟随 / 模式 / 命中计数) 与
**瞬时反馈** (notice)。notice 有**独立视觉** (警示色 + 与正文可辨的呈现)。
`th.text_secondary()` 兼两义的问题在此收口 (token 槽位由 M1.4 提供)。

**不变量**: notice **不改变状态栏几何高度** (不许因提示把状态栏顶高 —— 这会动截图取景);
两者同屏时**可辨**。

### 接入清单 (逐条给「为什么不行」)

| 条 | 触发 | 现状 | 要说什么 |
|----|------|------|---------|
| **P20** | 列表区**末行下方空白**单击/双击 | 完全沉默 (`view.rs:1527-1568`) | 说清「这里没有行」 |
| **P21** | 点侧栏**不可点**桶行 | 被吞 (`histogram.rs:456-458`) | 说清该口径为何不可点选 |
| **P22** | 点表格**无 glyph 行**的行首展开区 | 发了 `ToggleExpand` 却零反应 (`view.rs:1531` 不校验可展开) | 说清「本行无嵌套可展」 |
| **P23** | 纯 `.log` 按 **Ctrl+T** | 毫无反应 (`main.rs:1349-1351`) | 说清「本文件非 JSONL」 |
| **P24** | **→/←** 在明文行 / 无嵌套行 / parse 失败 | 提前 return (`main.rs:476-482`) | 说清该行为何不可展开 |
| **P25** | **Ctrl+G** 无书签 | 毫无反应 (`main.rs:1066-1075`) | 说清「尚无书签」 |
| **P26** | **空态**下 Ctrl+F / T / B / G / 方向键 | 一律丢弃 (`main.rs:1242-1245`) | 说清「尚未打开文件」 |
| **P33** | 栏持焦时 Space / ↑↓ / Home / End 语义反转 | 无提示 | 说清当前焦点下的键义 (至少 ↑↓) |
| **P34** | **Ctrl+A** 在分栏持焦以外 | 被 `main.rs:1247-1263` 静默吞掉 | 说清「行多选在 v1.x」(与 ROADMAP §四 同口径) |

**判据化**: **任何被吞掉的输入都要有原因** —— 这条写成守卫, 而不是逐条靠人记。
**先例**: 本仓已有「正则无效」进底栏 (`main.rs:1006-1008`), 本模块是把这条**从孤例升格为规则**。

**验收**: ① 上述 9 条各一条断言「触发后 notice 非空且含原因」; ② notice 与常态信息的
**可辨守卫**; ③ 状态栏几何不变的回归锁。

### 裁决补记 (2026-09-15, build 期)

**(1) P33 改判: 不走 notice 通道。**

上表把它与其余八条并列, 但那八条是**拒绝** —— 动作没生效, 说清为什么。P33 是**改道**
—— `Space`/`Home`/`End` 生效了, 只是被输入框收下。用拒绝的口吻说改道是在说一句不准确
的话; 而键路径上**没有「用户是想翻页还是想打空格」的判据**, 只能按键触发 → 每打一个
空格刷一条底栏提示, 写过滤正则时底栏会一路闪。

改法: 栏持焦时栏内右侧**常驻**一条键义提示 (随焦点出现/消失), 与 P6 的焦点线同批,
共用 `TextInput::is_focused()` 判据。验收随之改为「持焦时提示**画出来**且让位于输入区;
失焦时不画; 窄窗放不下则只留焦点线」。

**框架改动授权未用上**: 查证发现 `TextInput::is_focused()` 早已是公开 API, 且其 doc
明确写着焦点态描边本就该由外层容器画 —— 框架原设计即如此, 故本次零框架改动。

**(2) T11 在实现期暴露两处「分通道」的字面反转**, 均已修并加锁 (详见 todo T11):
notice 曾被拼进 `status` 而 paint 又单独画一遍 (`画两遍`); `Info` 档曾与常态同色
(`同色即同通道`)。**教训**: 「分了通道」这件事不能靠命名与注释成立, 得由守卫数出来 ——
这两处编译期、运行期都不报错, 只是安静地做不到。

**(3) T13 落地为一张表** (而非散落的测试集): 键盘路径的吞键在
`main.rs::every_swallowed_key_says_why` 的 `rows` 里逐行登记, 每行必须写出**期望的原因
片段**。鼠标路径三条各有同构守卫并互相指路 —— 它们在各自组件的 `event` 里, 强行并进
一张表就得搭起整棵控件树, 那时测的已不是那三个站点本身。

## 5. M4 `input-attribution` (本仓)

### Objective

手势的**前提**与**归属**明确: 前提不成立时说清 (P19 P32), 归属不与左键混淆 (P29),
界面**已经承诺过**的手势补齐 (滚动条拖拽)。

### P19 ★ —— 一条完整的行为链断了

**触发链 (查证)**: 点一行 → **Esc** → **Ctrl+C**, 什么都不发生, 而**行高亮仍在屏上**。

- `src/view.rs:1609-1613`: LogView 的 Esc 分支只看 `selection / selected_cell / press /
  dragging`, **不碰 `selected`**; 全空则返回 `Ignored`;
- `danqing/src/window/handler.rs:446-450`: 未认领的 Esc → 框架清焦点;
- `main.rs:1247-1263`: Ctrl+C 无焦点时**不进组件**, 而 app 的 ctrl 分支只认 b/g/t。

**这是 intent 反面教材第 2/3 条的教科书形态**: 视觉说「这行是选中的」, 手势却既不做事也不说为什么。

**改法 (二选一, 见 §8 Open Q1)**:
(a) **Esc 一并清行选中** —— 屏幕上没有高亮了, 自然不该能复制; （推荐）
(b) Ctrl+C 不依赖焦点 —— 行选中在就复制。
**倾向 (a)**: 它让**视觉与行为一致**, 而 (b) 会让「焦点在哪」这件事更不可知 ——
而焦点不可知正是 M1/M3 要治的病。

**验收**: ① 「点行 → Esc → Ctrl+C」链路的端到端断言; ② 选中的**视觉与可复制性**永远同真同假
(这条写成不变量, 不只测这一个手势)。

### P29 —— 右键不再冒充左键

**现状 (查证)**: `src/view.rs:1516` 处理 MouseInput 时**不筛 button**, 右键 / 中键与左键
**同效** (行选中 / 开设置卡)。

**改法**: **只认 `MouseButton::Left`**。
**理由 (不是「什么都不做」就完事)**: 缺陷不在「右键没有菜单」, 而在
**左键的语义被一个没有任何 affordance 承诺的手势触发了** —— 界面从未暗示右键能做什么,
所以「右键无反应」不构成违第 3 问; 而「右键偷偷干了左键的事」是实打实的误导。
右键上下文菜单属**手势缺失**, 按 intent 单独立项 (§6)。

**验收**: 右键 / 中键在列表区 / 底栏 ⚙ 上**不产生**选中或开卡; 左键行为逐项不变。

### P32 —— 模态不被穿透

**现状 (查证)**: `danqing/src/window/handler.rs:418-425` 的 `app_key_filter`
在模态判定**之前**无条件跑; 本仓 `main.rs:1235` 的注释**自认了这点**。
后果: 设置卡开着时按 Ctrl+O **在卡片之上弹系统文件对话框**; Ctrl+F 把焦点按 id 送到
卡后**看不见的**输入框, 此后打字进的是它。

**改法**: 产品侧 `app_key_filter` 加 `settings_open` 守卫 (框架的 `app_key_filter` 是
应用回调, **产品侧守卫足够, 无需框架改动**)。

**不变量**: 模态开时, 全局键**要么在卡内被认领, 要么被明确吞掉** —— 不得穿透到卡后。
(Esc 关卡的既有行为**保持**。)

**验收**: 模态开时 Ctrl+O / Ctrl+F / Ctrl+T / Ctrl+L / Ctrl+B / Ctrl+G 逐个断言
**不产生卡后副作用**; Esc 仍能关卡。

### 滚动条拖拽 (新 —— 用户 2026-09-14 裁定 5 越界纳入)

**现状 (查证)**: paint 画了 track/thumb (`view.rs:1354-1398`), 但 `view.rs:1453-1624`
整段 event **无任何滚动条分支** —— 只能滚轮。

**裁定理由 (写进 intent 了)**: 界面**已经承诺**该手势 (拇指是跨平台的可拖 affordance),
补上它是**兑现承诺**, 不是新增功能。

**改法**: 新增 按下 / 拖动 / 释放 三分支 + **hover 态 + 按下态 + 光标 (PointingHand,
走 M1.1 的 API)**。位置数学**复用既有行锚定** (`row_at`, `view.rs:695-697`) ——
与 M2 的 S1 收口同源, **不另推一份几何**。

**不变量**: ① 拖拽**不改变选中行** (滚动不是选中); ② 拖到顶/底**夹取**, 不越界;
③ 拇指位置与内容偏移**互为逆运算** (往返一致)。

**验收**: ① 往返一致性断言; ② 边界夹取; ③ 拖拽期间选中行不变。
