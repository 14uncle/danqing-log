# SPEC-level-histogram: 级别直方图 (计数侧栏)

> 模块 id: `level-histogram` (地图与共享约定见 `../../SPEC.md`)。
> 依赖 `core-viewer` 的 mmap 引擎、`jsonl-table` 的列发现与字段提取、`async-open` 的
> OpenJob 管道、`live-tail` 的增量索引能力。构建序排这些之后。
> 2026-09-12 用户发起 spec 技能立项; 同日裁决四项 (见「设计决策」D1–D4)。
> 立项理由与不可替代性: `docs/ROADMAP-v1x.md` §一。

## Objective

给一个「这个文件里有多少错」的一眼答案。

现状: 级别着色 (`view.rs` 的 `level_color` / `level_cell_color`) 只把**当前可见行**染色,
用户想把「错误到底有多少、占多大比例」问出来, 只能滚一遍或搜一遍 —— 483 万行的文件里
这是不可能完成的任务。而「一眼知道该看哪行」正是排障的第一个动作, 也是 LogViewPlus
最值钱的一个功能 (其截图: Info 4,544,133 / Error 43,464 / **Fatal 4,760**)。

本模块把计数从「渲染期逐可见行」提前到「打开期全文件一次算清」, 并在左侧常驻侧栏呈现,
JSONL 模式下点柱条即可跳到该级别的筛选结果。

**为什么必须免费**: 免费层缺它, 「不比 LogViewPlus 差」这句话当场就说不出口 —— 详见
`docs/ROADMAP-v1x.md` §一 改判块。它是 2026-09-12 从 v1.x 欠账改判进 v1.0 的项。

## 范围

**In**:

1. **级别分类器** (`classify_level`): 单一谓词, 返回 6 桶之一, 供计数与柱条配色共用。
   桶与优先级 (首个命中即定, **不重复计数**):
   `FATAL` > `ERROR` > `WARN` > `INFO` > `DEBUG`/`TRACE` > `其他`
   - 判据区间: **行前 200 字节** (沿用 `level_color` 的既定区间, 日志级别几乎都在行首)
   - `DEBUG` 与 `TRACE` **合并一桶** (两者在既有配色里同为灰 `trace_fg`, 拆开无信息增量)
   - `FATAL` 与 `ERROR` **拆开** —— FATAL 才是「一眼」要抓的那一行 (LogViewPlus 把它单列),
     两者共用红色 `err_fg`
   - **`INFO` 必须成桶**: 直方图的全部意义是比例, 没有基线就看不出错误有多稀少。
     注意这与 `level_color` (原始模式整行着色) **有意不同** —— 后者把 INFO 降噪到默认色,
     是用户已验收的降噪策略, 本模块**不改它** (见 Boundaries)
2. **计数通路, 按模式分两支, 都在异步打开管道内, 都是一趟独立的并行扫描**
   (核心决策 D2 + D6, 见下):
   - **原始文本**: 行首 200 字节按子串分类
   - **JSONL (检出且存在 level 类列)**: 列发现后按**字段值**分类, 复用 `extract_field`
   - **两支共用同一套并行骨架**: `[0, line_count)` 切 N 段 → N 线程各用
     `LogFile::lines_from` 迭代分类 → 归并。**不改兄弟 crate** (D6)
3. **增量维护**: tail 追加 → 只算新行并累加 (原始走索引钩子天然覆盖; JSONL 走
   `lines_from` 式起点步进, 不重扫前文); 轮转/截断重建 → 随重建重算。计数与视图同批次
   换入 (沿用 live-tail 的原子快照一致性原则), 不得出现「行数已更新、计数还是旧的」
4. **左侧常驻侧栏**: 固定宽度 ~112px, 6 行 = 级别名 + 计数 + 横条; 顺序按严重度降序
   (FATAL 在最上)。计数为 0 的桶**仍然显示** (「FATAL 0」是信息, 不是噪音)
   - 横条宽度按**对数刻度**归一 (D4) —— 线性刻度下 Info 4,544,133 会把 Fatal 4,760
     压成亚像素, 而后者恰恰是唯一要抓的
   - 配色复用既有语义色: FATAL/ERROR `err_fg` · WARN `warn_fg` · INFO `info_fg` ·
     DEBUG/TRACE `trace_fg` · 其他 正文色
   - 不与现有四区布局 (过滤栏/表头/虚拟化行/状态栏) 冲突: 侧栏是虚拟化行区的**左邻**,
     表格模式下与表头对齐
5. **点选联动** (D3): **JSONL 模式**下点某个级别柱条 = 套用既有 `level=<NAME>` 过滤语法
   (零新过滤通路); 再次点击当前生效的那一行 = 清除该过滤。原始文本模式柱条**纯展示**。
   `其他` 桶**两种模式都不可点** (无对应过滤语法)
   - 当前生效的 `level=` 过滤对应行高亮, 给「我正看着哪一档」一个落点
6. **开关与持久化**: `Ctrl+L` 切换侧栏显隐 (与既有 `Ctrl+T`/`Ctrl+O`/`Ctrl+F`/`Ctrl+B`/`Ctrl+G`
   不冲突); 开关状态落 `config.toml` (复用 `src/config.rs` 现有主题持久化通道)
7. **主题适配**: 深浅两套主题下 6 行全部可辨识 (沿用 `Theme` trait 取色, 不自定义颜色)

**Out**:

- **原始文本模式的按级别筛选** —— 要新造一套「按级别筛行」通路 (与现有正则搜索、JSONL
  字段过滤三者的关系要理清), 范围足够再开一个模块 spec; 本模块原始模式柱条只读
- 时间维度 (按时间分桶的趋势图/迷你图); 级别之外的字段分布 (那属付费层「字段分析」);
  柱条 hover 高亮与动画; 侧栏宽度可拖拽调宽
- 计数结果持久化 (每次打开重算即可, 1GB 亚秒级)
- 其他桶以外的「未识别但可疑」启发式归类

## 设计决策

四项均为 2026-09-12 用户裁决。

- **D1 位置 = 左侧固定侧栏** (备选: 表头下可折叠计数条 / 状态栏点开浮层)。
  裁因: 横条才有一眼的空间感; 浮层版把排障第一动作从一动作变两动作, 与初衷相背。
  代价是压窄内容区, 已知并接受 —— 表格模式本来就有 16 列要横滚。
- **D2 计数按模式分两支, 但都进 OpenJob**。裁因是**一致性红线**:
  - JSONL 若按原始字节子串计数, 一条 `{"level":"INFO","msg":"handle error failed"}`
    会被计进 ERROR 桶; 而点该柱条应用的 `level=ERROR` 是**字段**过滤, 结果里没有这行 ——
    **柱条数字与筛选后行数当场打架**。这是会立刻被用户发现的 bug, 不是理论风险。
  - 故原则: **计数口径必须与点选后筛选结果的口径一致**。JSONL 有 level 类列 → 按字段值;
    原始文本无结构 → 按子串; 各自与自己的可点行为对齐 (原始文本不可点, 故无对齐义务)。
  - 两支都在 OpenJob 内完成, UI 侧只见「就绪/未就绪」, 不暴露两条路径的差异。
- **D3 点选只给 JSONL 模式**。裁因: 复用现成 `level=ERROR` 语法零新功能;
  让原始模式也能点等于新造过滤通路, 该另开 spec。
- **D4 对数刻度横条**。裁因: 线性刻度会把 Fatal 压到看不见, 而它是唯一要抓的;
  计数数字始终以文本完整显示, 横条只表相对量级。
- **D6 计数 = 独立并行扫描, 不进索引趟, 也不改兄弟 crate** (2026-09-12 plan 阶段
  读码后改判, 原 D2 的「原始文本搭索引扫描便车」作废)。改判理由:
  - **便车搭不上**: `build_line_index_with` 的扫描只对字节做 `\n` 的 memchr, **不读行内容**;
    要分类就得逐行取行首 —— 是一趟货真价实的 O(bytes) 工作, 不存在「顺带」。
  - **且有数量级代价**: 参照物是 `run_filter` 的 74ms/GB, 但那是**并行**跑出来的
    (`jsonl.rs` 的 `PARALLEL_FILTER_THRESHOLD` / `MAX_FILTER_THREADS = 8`)。顺序遍历 +
    行首 200 字节内匹配 5 个关键词, 是 8 倍量级成本 —— **300–600ms/GB**,
    会把已发布口径的索引 77ms 变成 400ms+ 污染发布素材。
  - **改判收益**: 独立并行扫描约 50ms 量级, 索引数字**一个字节不动**,
    且不碰 `IndexHooks` 公共 API → **零跨仓改动**, 省掉兄弟 crate 提交 + `cargo update` 链路。
  - **仍然守 D2 的一致性红线**: 变的是「在哪算」, 不是「按什么口径算」。

## 成功判据

- [x] 单测: 分桶优先级与唯一性 —— `FATAL` 先于 `ERROR`; 一行含多个级别词只计一次;
      含干扰子串 (`informational`/`errors`) 的行不误判
- [x] 单测: **分类完整性** —— 6 桶之和 == 文件总行数 (其他桶兜底不漏不重)
- [x] 单测: **增量等价** —— 「全量计数」==「增量追加 N 行后计数」(原始与 JSONL 两支各一组,
      多轮对拍; **已知例外见下方「已知局限」**)
- [x] 单测: JSONL 字段口径 —— 构造 `level=INFO` 但正文含 `ERROR` 的对抗样本,
      断言其计入 INFO 桶 (钉死 D2 的一致性红线)
- [x] 单测: 轮转/截断重建后计数 == 重建后文件的全量计数
- [x] **索引零回归** (D6 判据) —— **原文措辞已修订**: 原写「与 2026-09-11 基线
      (明文 77ms / JSONL 88ms) 一致」, 但该基线**今日不可复现** (同一二进制跑出
      81–95ms 的漂移), 照字面判定会得出「回归了」的错误结论 —— 判据不可评 = 假绿灯。
      改为: **带计数代码与 `git stash` 去掉计数代码的两次构建, 在同会话内对拍无差异**
      (实测: 有计数 明文 95/92/95 · JSONL 121/96/101; 无计数 93/93/95 · 92/90/95, 同噪声域)。
      后续同类判据一律做同会话 A/B, 不与历史数字比
- [x] **计数成本实测落档** (不估算): 1GB **明文 94ms** · JSONL 行口径 **76ms** ·
      JSONL 字段口径 **112ms** (9090 MiB/s)。判定线 **≤150ms** → 随 `OpenOutcome`
      一起交付, 「先显示文件、计数随后补入」的改判**未触发**
- [ ] 人工验收: 1GB JSONL 打开 → 侧栏出现且 6 行计数正确 (与 `wc`/过滤结果交叉核对)
- [ ] 人工验收: JSONL 点 ERROR 柱条 → 表格筛出该级别, **底栏行数与柱条数字一致**
      (D2 红线的端到端验证); 再点一次 → 清除
- [ ] 人工验收: tail 追加新行后计数随之变化; 外部截断/轮转后计数与重建结果一致
- [ ] 人工验收: `Ctrl+L` 显隐; 重启后开关状态保持; 深浅两套主题下 6 行均可辨识
- [x] 三件套绿 (`cargo fmt` + `cargo clippy -- -D warnings` + `cargo test`) —— 84 绿

## 已知局限

- ~~增量漏计「被补全的半行」~~ —— **2026-09-12 review 发现、复现并已修**。
  旧快照末行若以无换行结尾, 外部把它补全时会改判该行 (半行 `... 12:00:01 `
  补成 `... 12:00:01 ERROR disk`), 而纯增量 `[old_line_count, new)` 不含该行,
  于是它永不重算 —— tail 长会话下侧栏静默偏低。
  修法: **重算起点退一行** (`levels::update_for_append`), 即
  `old_counts − 旧重叠区间分类 + 新重叠区间分类`; 旧尾本就完整时减旧加新相抵,
  故**无条件启用**安全 (不需要先判旧尾是不是 `\n`)。
  计数与过滤**必须同起点**: 过滤侧先摘掉 `>= 起点` 的旧命中再重跑同区间
  (`main.rs` 的 `drop_filter_hits_from` + `append_filter_hits`), 否则重叠行
  漏算或重算 —— 前者正是 review 前两侧同步漂移掩盖掉的形态。
  连带收敛: `OpenOutcome.level_counts` 从「按臂而定 (增量/全量)」改为
  **一律绝对量**, 落点只覆盖, 「增量当全量用」的误用空间消失。
  回归: `update_for_append_covers_completed_half_line` (明文 + 字段两支)、
  `append_outcome_covers_completed_half_line` (worker 路径)、
  `apply_appended_covers_completed_half_line_on_both_sides` (应用层两侧 + D2)、
  以及多轮对拍里插入的「半行 → 补全」一轮。
- 前缀口径偏宽 (`ERRORS`/`INFORMATIONAL` 计入 ERROR/INFO 桶) —— 这是 D7 换来
  「`WARNING` 能命中」的代价, 一致但柱条标签略微夸大所计内容。

## Boundaries

- **Always**: 注释/文档中文; 新 `.rs` 文件头 `//! @author 十四叔` + `//! @date yyyy/MM/dd`;
  提交前三件套 (`cargo fmt` + clippy 零警告 + 测试全绿)。本模块按 D6 **只动
  `danqing-log` 单仓**, 不触发跨仓提交链路
- **Ask first**: 新增/变更键位 (`Ctrl+L`); 变更 `config.toml` 的字段格式;
  若实测触发「先显示文件、计数随后补入」的改判 —— 那会引入新的 UI 状态与一条作业失效链,
  需复核后再改
- **Never**: 改 `level_color` / `level_cell_color` 的既有配色策略 (INFO 在原始模式降噪
  是用户 2026-09-06 验收过的有意行为); 给原始文本模式新造过滤通路 (属另一模块);
  把计数做成 UI 线程的同步二次扫描 (会破坏 async-open 的「全程可响应」承诺);
  自定义颜色绕开 `Theme` trait

## 设计决策 (build 阶段追加)

- **D7 字段口径 = 前缀匹配 + `col=TOKEN*` 子句** (2026-09-12 读码后定, 取代原「字段值按
  `classify_level` 子串分类 + 子句写 `level=<NAME>`」)。裁因是 D2 红线: 过滤的扁平等值
  是**字节全等**, 于是文件里写 `WARNING` 时柱条数得到、`level=WARN` 却筛出 0 行。
  改成前缀匹配 + 前缀通配子句后, 两边对同一 token 走同一判断 —— **一致性成为构造保证**,
  且不需要 per-file 观察值。六个 token 首字母互不相同 (F/E/W/I/D/T), 前缀匹配天然互斥。
  → 连带的**新不变量** (已在代码与测试中体现): **计数口径必须全程一致** ——
  `OpenOutcome` 携带 `level_column`, 落点据此重建子句表, 也据此决定后续增量追加走哪条口径。
- **D8 窄窗自动折叠** (原 Open Question 二选一): 内容宽 < 640px 时侧栏宽度归零, 优先保
  内容区 —— 新用户未必知道有 `Ctrl+L`, 卡在没法看的布局里比看不到直方图糟。
  显隐判定只留一处 (`effective_width`), paint/event 只看 layout 给的宽度。

  观察值)。倾向暂不动 —— 排障要抓的是 ERROR, DEBUG 可点性价值低。
