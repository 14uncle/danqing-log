## Overview

把「每个手势有没有反馈」扫一遍并清零。框架侧补**两条**通路 (光标形状 API /
`collect()` 认模态屏障, M1); 产品侧四态分通道 (M2) /
拒绝要说清 (M3) / 前提与归属 (M4) / 可发现性 (M5)。**进 v1.0, 阻塞发布**。
零新增依赖; 框架侧全部**只加机制、默认 off**, pomodoro 零波及。

## Architecture Decisions

- **D1: 光标 API 与焦点同源** —— `cursor_at(root, pos)` **复用 `hit_focusable` 那一趟
  `visit` walk** (`danqing/src/widget/focus.rs:199-249`), 同一套模态屏障 (`:222`) 与
  祖先裁剪 (`:214-219`), **不另推一份命中几何**。本仓 2026-09-14 刚为「命绘各推一遍」
  吃过一轮苦头 (S1–S3), 这里直接不制造第四个。
- **D2: `collect()` 对齐 `visit()`, 不新造规则** —— P31 的根因是**同一个文件里两条路
  分叉** (`collect` 不看 `modal_barrier`, `visit` 看)。修法是让它们一致, 而不是在
  `collect` 里写第二套屏障语义 —— 否则下次改屏障语义又要改两处。
- **D3: 四态分通道落在「产品语义取色函数」, 不在 paint 点调数值, 也~~不进框架
  `Theme`~~** (2026-09-14 实现期修正, 原文写的是「落在 `Theme` token」) ——
  M2 的六条病灶全是「两个语义共用一支取色函数」, 解法是**每态一支**;
  在 paint 处调数值会把语义重新糊回去, 且守卫无处下钩。
  **但那一支要放在产品侧**: 本仓分层是「框架给通用调色板 → `LogTheme` 转发 →
  产品语义色放产品侧函数」, 规矩写在本仓注释里 (`view.rs:126`
  「产品语义放产品侧」), 先例是 `row_band_bg`/`row_hover_bg`/`cell_highlight_colors`。
  **光照抄先例走 `row_hover_bg` 那一款** (浅/深两套值 + 产品侧守卫)。
  **浅色 `selection`↔`hover` ΔL\* 0.79 的已知例外保留** (浅色养不起六个两两 ≥3 的面) ——
  M2 只保证「同屏出现第三态时**可辨**」, 不承诺抹平这个例外。
- **D4: 拒绝反馈走状态栏瞬时通道, 不引入弹窗 / toast / 模态** —— 密度不许降
  (ui-redesign 用户原话); 且 notice **不改变状态栏几何高度**, 否则会动截图取景。
- ~~**D5: M1.3 回退是「新增对称开关」而非泛化既有 API」**~~ —— **2026-09-14 撤回**:
  读调用链发现**框架已有**未认领鼠标事件的回退 (`handler.rs:983-985`, 无条件),
  滚轮到达应用后被应用自己丢掉 (`main.rs:1222`)。**T3 撤销, P30 归 M4 产品侧修。**
- **D6: P19 修在 Esc 一侧** (Esc 一并清行选中), 不修 Ctrl+C 的焦点依赖 —— 让
  **视觉与行为同真同假**。不变量写成守卫: **「选中的视觉」与「可复制性」永远同真同假**,
  不只测这一个手势。
- **D7: 滚动条拖拽复用行锚定数学** (`view.rs:695-697` 的 `row_at`), 与 S1 的收口
  同源 —— 不另推一份位置几何。
- ~~**D8: token 槽位先在框架出现、取值在产品定**~~ —— **2026-09-14 撤回**:
  它建立在 D3 原判之上, 而 D3 的前提被读码否掉了 (见 D3)。**框架本批不新增任何 token。**

## 风险与注意

- **M1 是本批唯一跨仓改动**: 先 `cp tools/local-patch.toml .cargo/config.toml`
  再改 danqing (**patch 默认关, 忘了 cp 则本仓静默用旧框架** —— 农场教训);
  push 前在 danqing 内跑三件套 (**600 lib** + 集成 59 基线, 2026-09-14 实测)。
- **lock 陷阱两个形态都踩过** (2026-09-14): ① patch 开着时 lock 必为 path 态,
  **此态别提交**; ② 关 patch 后 `cargo update -p danqing` 可能报
  `package ID specification danqing did not match any packages` ——
  **先跑一次 `cargo check`** 让它按 manifest 重解, 再 `cargo update`。
- **RustRover 并发 cargo 抢 package cache 锁**会把 lock 写回旧 rev —— 报
  `could not find ... in danqing` 时重跑即顺, 验 lock 前关 IDE 自动 cargo。
- **T1 要先核实框架包装层**: `cursor_at` 作为 trait 方法需经 `Node` 透传,
  与 `focusable` / `modal_barrier` 同路 (那两个**已是先例**) —— 先确认包装层,
  再动其它三节, 否则接口要返工。
- **T1 的 apply 时机定为帧末**: 「鼠标不动但内容变了」(滚动 / 切主题 / 内容重排)
  时也要重算光标; 靠 `CursorMoved` 驱动会漏这些场景。
- ~~**T4 是「纯加槽位」**~~ —— **T4 已撤回** (见 D3/D8/任务表)。留下的教训:
  「框架先出现、产品后赋值」读起来顺, 但与**本仓的实际分层相反**;
  分层的判据在**代码注释**里 (`view.rs:126`), 不在架构直觉里。动工前先读那一段。
- **M2 的已知例外不许被当成缺陷修掉**: 行 hover 与斑马**独立通道**、
  侧栏不可点行**有意不给 hover**、表格**不做单元格词级框选** —— 三条都要有断言守着
  (防「改回」), 而不是顺手「修好」。
- **每任务完成跑三件套**; **所有 commit/push 点都标 ⏸ 待用户点头**。
- **本批 39 条无一条经运行态证实** —— M0 与最终核对单就是这件事的对策, 期间若
  实机推翻某条, **以实机为准并回写矩阵** (本仓规矩: 结论要有对照组)。
