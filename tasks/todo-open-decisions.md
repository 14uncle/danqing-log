### 我一开始把这条判错了 —— 记在这里免得复现

初判写的是「**`Dropdown` 弹层 hover 看不出在哪行**, ~1.10:1」。**判反了。**
`Dropdown` 那处恰恰是**唯一没问题的**: 它压在**近白弹层**上, 同一个值在那里是
Δ`L*` **3.72** —— 与用户在模块 5 已接受的浅色斑马 (3.49) 同一量级, 是好的。

错因: 拿 **WCAG 对比度**去量「大面积底色之间差多少」。对比度是**文字**指标
(小面积、高反差), 对大面积色差**严重低估** —— 同一个值算出来 1.10, 看着「等于
没有」, 换成 Δ`L*` 是 3.72。**指标用错了, 不是数错了。**

换 `ΔL*` 重查, 真问题在别处 —— **5 处, 全部压在页面底上**:

| 用处 | 浅色 ΔL* | 判定 |
|---|---|---|
| `view.rs:691` 表头底 | **0.74** | ❌ |
| `view.rs:1551` 过滤栏底 | **0.74** | ❌ |
| `histogram.rs:202` 侧栏「生效筛选行」 | **0.74** | ❌ |
| `settings.rs:178` 关闭按钮 hover | **0.74** | ❌ |
| `settings.rs:454` 链接行 hover | **0.74** | ❌ |
| (框架) `dropdown.rs:86` 弹层 hover | 3.72 | ✅ |

所以原值的毛病是**只对白底成立、对页面底不成立**, 不是「深了浅了」。

### 修法与依据

新值 `#E0E7E3`, 按**暗色那一支的台阶**取: 暗色 `surface_variant` 对暗底
Δ`L*` **+6.42**, 浅色这支 **−5.92** —— 两个主题第一次对齐。
对近白弹层它变成 8.97, 与已接受的行 hover (9.12) 同量级, 不嫌重。

新回归锁 `surface_variant_is_a_comparable_step_in_both_themes` (区间 [3, 10]),
用**新增的 `l_star_of`** 而不用对比度 —— 正是上面那个教训的固化。
**有牙齿**: 还原旧值 → 立刻红 (`0.74 落在 [3, 10] 之外`)。

> **本仓消费已重钉** ✅: 框架 `0d91ed7` push 后 `cargo update -p danqing`
> (`486d180d` → `0d91ed7e`), 两仓三件套全绿 (框架 583 lib / 本仓 112)。
> 过程中先开着联动 patch 验过一遍 —— 那是「改了但还没生效」期间的唯一验法。

**Blast radius 实际查过**: 五仓里只有**已终止的** `danqing-clipboard` 用了 1 处,
其余四仓 (pomodoro / disk / tile / xirang) **零处** —— 实际只影响本仓。
这条推翻了我写「没动的理由」时的猜测 (当时写「pomodoro 等同吃」, 是**没查**)。

## D2 · 浅色语义色也 sub-AA —— **已裁已修 ✅**

> 裁决: 2026-09-13 用户「D2 一并处理」。走 ①**按 AA 压暗色板**
> (不是 ② 接受, 也不是 ③ 只提一部分)。产品侧 `src/view.rs` 的 `LevelPalette`
> **两套浅色口径各压一遍**, 回归锁
> `light_semantic_colors_clear_wcag_aa_on_light_surfaces`。

### 判据 (与暗色**同一把尺**)

语义色是**文字**, 但按它实际压着的**面**分两档:

- **常驻面** (页面底 `#F0F8F6` / 斑马行 `#E6EEEC`) —— 要 **WCAG AA 4.5**
- **瞬时面** (hover / 选中行) —— 只要 **3.0** (与框架侧选区带那条锁两头一夹)

**斑马行必须进常驻档**: 表里一半的行就是斑马底, 只量页面底等于**漏掉一半的行** ——
这与「面阶梯」那次翻车是**同一个错** (判据对页面底、而屏幕上挨着的是别的面)。

### 修法与依据

**保持 HSL 色相与饱和度, 只降亮度** (二分求最低亮度, 再留一点余量让护栏不贴在阈值上)。
所以是**同一批颜色变深**, 不是换一套色板 —— 琥珀还是那个琥珀、蓝还是那个蓝。
两条口径**各自独立压暗** (分叉是 D3, 不动它)。

| | 修前 (页面底 / 斑马) | 修后 (页面底 / 斑马) |
|---|---|---|
| ERROR | 5.34 / 4.88 | **不动** |
| WARN | 3.25 / 2.97 | 5.05 / 4.62 |
| OK | 3.78 / 3.46 | 5.06 / 4.63 |
| INFO | 4.38 / 4.00 | 5.05 / 4.62 |
| DEBUG | 3.09 / 2.83 | 5.04 / 4.61 |

ERROR 本来就过线, **一个字节没动** —— 改的每一支都有实测理由, 没改的也有。

### 有牙齿 (两次真红, 都验过)

- 还原 WARN 旧值 → `整行着色 口径 warn 压 页面底 只有 3.26 低于 4.5`
- 换成**只过页面底**的值 (`#936A11`, 页面底 4.52) → `压 斑马行 只有 4.13 低于 4.5`
  —— **斑马那条单独有牙齿**, 不是写来好看的

### 这条当初是被「选中行读不出来」照见的

审查浅色截图时发现选中的那行 `status=400` 读不出来, 一度当成**独立缺陷**
(「选中行上的语义色碰撞」)。算完才清楚 **它不是一个新问题, 就是 D2 在这里显形**——
那套值只对**白底**成立。当时压选中行: WARN 2.45 / DEBUG 2.34 / OK 2.86 /
INFO 3.31 / ERROR 4.04; **修后 3.82–4.04**。

关键在**上限**: 浅色 WARN `L*` 58.6 属中亮度, 压在**任何近白底**上最高也只有 3.34 ——
所以「把选区带调淡」治不了它 (实测 α 0.30→0.20 只从 2.40 到 2.66),
**要修只能修色板本身**。这次就是修在色板上。

### 连带 (同批)

- 框架 `DarkTheme::selection()` 的注释原先拿「浅色 ERROR 红 4.04」**一支**推出了
  「中亮度前景本来就够」, 实测 WARN/DEBUG 只有 2.45 / 2.34 —— 已换成实测版
  (danqing `47a5537`)。**结论「浅色不动」不变, 换掉的是理由**;
  那句里的「合成后是 (242,238,235)」与代码也对不上 (线性合成实为 (205,219,217))。
- `level_color_prefers_error_over_info` 原先用**通道阈值**认颜色 (`warn.g > 0.4`),
  压暗后**假红** (分类明明是对的)。已改成断言「判到哪一支」, 顺带补了原先漏测的
  TRACE —— **分类与取值分开测**, 取值归上面那条锁管。

## D3 · 浅色两条着色路径的值本来就分叉

「整行着色」(`level_color`) 与「单元格/状态着色」(`level_cell_color` / `status_color`)
**原先各写了一套字面量**, 且它们不一样:

| | 整行着色 | 单元格 | Δ`L*` | Δ`E76` |
|---|---|---|---|---|
| ERROR | (191,46,46) | (194,54,54) | 1.66 | **3.43** |
| WARN | (179,128,20) | (184,128,5) | 0.55 | **4.15** |
| DEBUG | (140,140,148) | (143,143,153) | 1.21 | 1.65 |

JND ≈ 2.3 —— **前两支可感知** (虽然两种模式不会同屏出现, 所以用户没发现)。

**当时的「没动的理由」已经不成立了**: 那时写「合并任一支都会改浅色的既有观感,
与『现值一行不动』冲突」—— 但 D2 已经**主动**改过一遍浅色了, 这条理由随之作废。
本轮做法是**原样保留两条口径**, 在 `view.rs` 的 `LevelPalette` 里把它们并成两个
构造函数 (`light_line()` / `light_cell()`) 并写明来源; 暗色是全新的没有包袱,
**两条路径共用一套**。

**D2 压暗之后分叉没有自己消失** (实测 `ΔE76`: ERROR 3.43 → **3.70** /
WARN 4.15 → **3.42** / DEBUG 1.65 → 1.20): 两条口径都过 AA 了, 但**仍然不是同一个
颜色**, 前两支还在 JND 之上。别指望它随别的工作一起收敛。

**要裁的**: 合并到哪一支 (或都不合并, 永久保留两套)。现在**只差一次选择** ——
合并不再有观感代价以外的顾虑 (反正两支都已过线, 差异落在 JND 边缘)。

## D4 · 框架 `composite_over` 混在 sRGB 空间, 不是线性

`danqing/src/theme.rs:84` 的公开函数 `composite_over` 直接对**存储分量**
(sRGB 编码) 做 over 运算。但模块 1 之后 **GPU 在 linear 空间混合**。
两者不是一个东西:

- 它自己的测试 `composite_over_half_white_on_black_is_mid_gray` 把这个旧行为
  **钉死了** (线性混合下 50% 白压黑应为 ≈187, 不是 128)。
- 而 `contrast_ratio` 的文档 (`theme.rs:75`) 恰恰写着
  「半透明色请先经 `composite_over` 合成到底色再比较」—— **照着做就是量错对象**,
  正是「护栏全绿、屏幕全灰」那类事故的入口。
- `SceneTheme::surface()` (`theme.rs:638`) 也用它做构造期推导。

**现状**: 本仓新写的守卫一律绕开它, 自备线性合成
(`view.rs` 测试里的 `composited_luminance`), 并在注释里标明「别用它」。

**要裁的**: ① 改 `composite_over` 为线性 (要同步改它自己的测试 + 复核
`SceneTheme::surface()` 的输出变化) / ② 只修文档, 把陷阱写明 / ③ 加一个
线性版本另起名字, 旧的标 deprecated。
